    Tokenizer Playground：一句话是怎样被拆成 Token 的

    Published: September 18, 2026

    在很多大模型介绍里，tokenization 只占流程图最左边的一小格：输入一句话，把它切成 token，然后交给模型。后面的 Attention 和生成过程通常更吸引人，这一格就很容易被快速带过。

    但只要实际用过模型，就会遇到一些细小的疑问：为什么一个英文词有时会被拆开？中文一定是一个字一个 token 吗？没有见过的新词还能不能表示？同一句话换个 tokenizer，token 数为什么又变了？

    这些问题让我觉得，分词本身也值得有一个可以停下来观察的地方。于是我做了 Tokenizer Playground，从字符出发，亲手训练一组 BPE 合并规则，再拿它处理新的文本。想看的不仅是最后切成了什么，还包括这些切法是怎样一步步形成的。

    先让词表从很小的地方长出来

    这个实验选择了一个便于解释的版本：以 Unicode code point 为起点，按空白预先拆分文本，并给每个非空白片段加上词尾标记。这里的初始单位近似于日常说的字符，但一个视觉上完整的复杂 emoji 也可能包含多个 code point。

    接下来，把训练语料中所有相邻符号对找出来，按出现频次排序。选中最高频的一对，把它们合成一个新符号，然后重新统计。重复这个过程，一些经常一起出现的片段就会逐渐成为更大的单位。

    这也是我觉得 BPE 很适合做成交互实验的原因。它的每一步都很局部：只合并一对符号。但许多局部选择累积起来，词表的形状就改变了。页面里既能看到当前拆分，也能看到接下来最可能发生的合并，因此不用跳到最终结果才知道发生了什么。

    最常见的片段，未必最像一个完整单词

    内置的 Classic words 使用 low、lower、newest、widest 这一组经典词汇。相同单词在语料里可以重复出现，统计词对时会把词频算进去，而不是每一种拼写只记一次。

    逐步执行前五次合并，可以看到 e + s、es + t、est + 词尾标记 先出现，选择时的频次都是 9；随后才是频次为 7 的 l + o 和 lo + w。从读者的直觉看，low 已经是一个完整单词，好像应该更早出现。但算法只按照当前的相邻频次做选择，不会额外判断哪个片段更像词。

    这段历史很重要。BPE 得到的不只是一个装着片段的集合，还有这些片段按什么顺序形成的规则。每次合并之后重新计数，下一轮面对的已经是新的符号序列。

    界面支持播放、暂停和回退，也可以修改 Merge budget。如果某一步让人意外，可以退回去看：究竟是哪几个词贡献了这对符号的频次？语料里的重复，又怎样改变了它被选中的机会？

    把规则拿去处理没见过的词

    训练和使用 tokenizer 是两件相关但不同的事。

    训练时，要在语料中统计频次，决定规则。处理新文本时，则使用已经学到的规则，并按照训练所得的顺序应用，不会再根据新句子重新挑一套最高频片段。

    页面里的 Encode unseen text 就是为这个区别准备的。在英文案例中输入 lowest newer，逐步增加训练轮数，可以观察它如何复用此前学到的片段。新词不必以完整形式出现在训练语料里，也可能被拆成几个熟悉的部分。

    切换到 Chinese research，再观察 金融研究者。截图中的实验完成了六次合并，最终得到 金融、研究、者 三个片段。这个结果来自当前小语料的频率和规则顺序；改掉语料，或者停在更早的轮次，切分就可能不同。

    所以，token 既不天然等于一个词，也不天然等于一个字。它的粒度受到训练材料、预处理方式、算法和规则数量共同影响。把这些条件放回去看，分词结果就不再显得任意。

    一个很短的输入，也能暴露实现细节

    自定义语料里可以试试 aaa aaa aa a。它很短，却能让两个容易混淆的动作分开。

    统计时，一个 aaa 中有两个相邻的 a + a，它们共享中间那个字符；两个 aaa 加上一个 aa，这一对的加权频次合计是 5。执行合并时，却要从左到右进行非重叠替换：同一个字符不能同时参与两次合并，因此每个 aaa 只能变成 aa 加 a。

    换句话说，频次为 5 并不意味着这一轮会完成五次替换。这个例子很适合检验自己是否真的理解了“统计出现”和“应用规则”之间的差别。动画只是把符号移动起来，背后的计数规则仍然需要准确。

    另一个可以尝试的方向是空格、换行和 emoji。实验把空白片段单独保留，遇到训练时没有出现的字符，也会保留原字符并给出提示。这样既能观察已知规则如何工作，也能检查原始输入是否还原成功。

    “无损还原”在这里是文本表示层面的检查，并不意味着模型理解了这句话。保留未见字符也是这个教学实现的选择，真实 tokenizer 可能采用字节回退、未知符号或其他机制。

    这个 Playground 想回答到哪里

    除了英文和中文，项目还提供了一组代码相关词汇，包括 token、tokenization、encoder 和 decoder，也允许编辑最多 1200 字符的语料。训练和编码全部在浏览器本地完成，输入不需要上传。

    它采用的是字符起步、空白预分词、带词尾标记的教学 BPE，不能直接等同于 GPT 系列的 byte-level BPE，也不能代表 SentencePiece 的具体配置。页面显示的 token 数适合比较当前实验，不适合拿去估算任何线上模型的计费。

    我希望这个项目留下的，是一种阅读分词结果的习惯：看到一个切分，先问规则来自哪份语料，符号怎样被合并，边界又怎样处理。这些条件清楚了，“文本变成 token”就不再是流程图里匆匆经过的一格，而是一段可以自己训练、回放和验证的过程。
