    Transformer Architecture Lab：把 Attention 变成可以观察的过程

    1 minute read

    Published: September 18, 2026

    最近我做了一个小项目：Transformer Architecture Lab。如果用一句话概括它，我更愿意说：这是一次把 Attention 变成可以观察的过程的尝试。Transformer 已经变成今天大模型、Agent、RAG 和多模态系统背后的基础结构，但很多时候，我们谈它时仍然停留在几个熟悉的词上，比如 attention、multi-head、encoder、decoder、next token prediction。

    这些词当然重要，只是如果它们彼此之间没有连起来，理解就很容易停在“听过”和“会说”的层面。我更想做的是把 Transformer 拆成一个可以操作的实验室，让人不是被动读一段解释，而是能顺着一个例子看到：文本怎样变成 token，token 怎样进入 embedding，Q/K/V 为什么要拆开，attention weights 怎么经过 softmax 变成信息路由，多头机制又为什么不是简单重复几遍同一件事。也就是说，让 Attention 不只是一个公式名，而是一段能被追踪、比较和验证的计算过程。

    为什么想做这个项目

    我之前写过 AI 时代学习和基础能力的问题，里面有一个很核心的判断：越是强大的工具，越需要人保留对底层机制的理解。否则我们很容易把一个系统当成黑盒，只看它给出的结果，却不知道它为什么能工作，也不知道它什么时候会失效。

    Transformer 就是一个很典型的例子。现在很多人每天都在使用基于 Transformer 的模型，但真正解释起来，常常会卡在几个地方：self-attention 到底在“看”什么，Q/K/V 分别承担什么角色，为什么 decoder 不能看未来 token，encoder-decoder 和 decoder-only 模型到底有什么差异。

    所以这个项目不是为了把论文复述一遍，也不是为了做一个炫技页面。更准确地说，它是一个学习工具：把抽象结构变成可观察的流程，把公式背后的信息流尽量可视化，让理解从“概念记忆”往“机制直觉”靠近一点。这也是标题里“把 Attention 变成可以观察的过程”真正想表达的意思。

    我怎么拆 Transformer

    项目里我把 Transformer 拆成了一条连续链路：

    Raw text -> tokens -> embeddings + positions -> Q/K/V
-> scaled dot-product attention -> multi-head merge
-> residual + normalization -> feed-forward refinement
-> encoder / decoder output

    这条链路看起来很长，但它的好处是每一步都有明确的输入和输出。比如 tokenization 解决的是“自然语言怎么变成模型可以索引的离散符号”；embedding 解决的是“编号怎么变成可计算的连续向量”；position encoding 则提醒我们，attention 本身并不天然知道顺序，所以必须额外注入位置信息。

    到了 Q/K/V，项目里用了一个更直观的说法：Query 像“我要找什么”，Key 像“我如何被匹配”，Value 像“我真正提供的信息”。这种解释不一定是最学术的表达，但它能帮助第一次接触的人先建立角色感。真正进入 Math Console 时，仍然可以看到 QK^T / sqrt(d_k)、softmax、attention weights 和 context vector 的计算路径。

    交互比静态解释更适合这个主题

    Transformer 难懂的一部分原因，是它不是单点概念，而是一组关系同时发生。一个 token 会看很多 token，不同 head 又会从不同角度看同一句话。静态文章可以解释，但很难让人形成“流动”的感觉。

    所以我在项目里放了几个内置案例：

    • Pronoun Reference：看 it 为什么更应该指向 animal，而不是 street。
    • Machine Translation：看 encoder 如何理解英文，decoder 如何生成中文。
    • Next Token Prediction：看自回归生成为什么必须遵守 causal mask。
    • Long Context Dependency：看长距离指代不必一步步传递。
    • Chinese Tokenization：看中文 token 粒度为什么不能简单按空格理解。

    这些例子不是为了模拟一个真实大模型的全部参数，而是为了把结构讲清楚。项目中的 attention 计算用了 deterministic mock embeddings，也就是说它不是训练后的真实权重，但矩阵形状和计算顺序是按 attention 机制来的。这样做的取舍是：牺牲一部分模型真实性，换来更高的可解释性和可复现性。

    技术上做了哪些取舍

    这个项目用的是 React、TypeScript 和 Vite，动画部分用了 Framer Motion，图标用 lucide-react。整体设计我刻意做成轻量的 research cockpit，而不是厚重的工程后台。因为它首先是一个理解工具，不是一个模型训练平台；界面应该让人愿意停下来观察，而不是被过多控件淹没。

    几个我比较在意的点：

    • 交互必须围绕机制，而不是为了动效而动效。
    • 每个模块要讲清楚自己解决什么问题、输入是什么、输出是什么。
    • Math Console 不能只是装饰，要能看到 embeddings、Q/K/V、scores、weights 和 context vectors。
    • Multi-Head 不能只画多个圆点，而要能打开或关闭不同 head，看到不同关系视角。
    • Encoder 和 Decoder 要放在同一个视图里比较，尤其是 causal mask 和 cross-attention 的区别。

    这些取舍背后其实还是同一个原则：复杂概念可以被做得好看，但不能因为好看而变得更模糊。

    这个项目对我自己的意义

    做这个项目时，我也重新整理了一遍自己对 Transformer 的理解。很多概念看起来熟悉，但真正要把它变成一个别人可以操作、可以看懂、可以顺着例子走下去的页面，就会发现自己必须重新追问很多细节。

    比如，为什么 Q/K/V 的解释容易误导？为什么 attention weight 不等于最终答案？为什么 residual 和 normalization 不应该被当成“后处理”？为什么 decoder 的 causal mask 是生成任务的基本约束，而不是一个可有可无的技巧？

    这些问题在写代码时会变得很具体。一个模块标题怎么写，案例如何选择，动画速度怎么控制，矩阵结果要展示到什么程度，都在逼迫我把“我知道”变成“我能讲清楚”。这也是我喜欢做研究型原型的原因：它不只是展示结果，也会反过来校准自己的理解。

    从这个实验室继续往外走

    这个版本更像一个基础实验室。沿着其中几个还想继续追问的问题，我后来又做了四个独立项目，也分别整理成了图文笔记：

    • Position Encoding Lab：看见位置如何改变 Attention，把 Sinusoidal、RoPE、ALiBi 放进同一个位置变换实验。
    • LLM Inference Lab：一次生成里，哪些计算可以留下来，追踪 KV Cache 的逐层执行与数值验证，并对比三类模型的信息流。
    • Tokenizer Playground：一句话是怎样被拆成 Token 的，从字符和频次出发，训练、回放并使用 BPE 合并规则。
    • LLM RL Lab：奖励如何一点点改变回答的概率，把采样、奖励、优势、裁剪与实际策略更新接起来。

    它们各自聚焦一个问题，也可以顺着文本表示、位置关系、推理复用和反馈学习连起来阅读。后面我还希望补上 attention matrix 导出，让实验结果更方便进入教学笔记和分析。

    如果说这个项目想表达什么，我觉得不是“Transformer 很复杂”，而是“复杂系统也可以被拆成一条可理解的链路”。只要把每一步的输入、输出和约束讲清楚，Attention 就不再只是论文里的公式，而会变成一个可以观察、可以比较、可以验证的过程。很多看起来遥远的 AI 概念，也能一点点落回可以思考的地方。
