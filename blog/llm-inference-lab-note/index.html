    LLM Inference Lab：一次生成里，哪些计算可以留下来

    Published: September 18, 2026

    看大模型逐字输出时，很容易产生一种感觉：模型读完了前面的内容，然后接着往下写。但如果把这个过程展开，会遇到一个很实际的问题：每增加一个 token，前面所有位置是不是都要重新计算？

    如果答案一直是“是”，长对话就会越来越昂贵。KV Cache 正是在这里发挥作用的。不过，“缓存历史 Key 和 Value”这句话虽然简洁，也容易把最关键的部分略过去：为什么旧结果还有效？每一层分别缓存什么？新 token 到来以后，究竟省掉了哪一步？

    做完 Transformer Architecture Lab 后，我把这些问题继续做成了 LLM Inference Lab。它把 KV Cache 和模型家族放在一起，因为能否复用历史计算，最终取决于模型允许哪些信息流动。

    先问旧结果为什么不会变

    在因果注意力里，一个位置只能读取自己和之前的位置。假设前缀、模型参数、位置规则以及前向计算方式都保持不变，后来增加的 token 对旧位置而言仍然不可见。

    这意味着第一层中，旧位置的输出不会因为未来多了一个词而改变。第二层读到的旧输入没有变，它的旧输出也不会变。沿着层数继续推下去，就得到缓存能够成立的理由：每一层历史位置的 Key 和 Value 都可以保留下来。

    所以缓存的依据藏在计算依赖里。仅仅说“文本看起来没有变”还不够；如果计算允许旧位置读取新位置，即使旧文本完全相同，旧的隐藏状态也可能需要更新。这个区别，恰好把推理优化和 Attention mask 连在了一起。

    跟着一个新 token 走完两层

    实验提供了句子和代码两个例子。句子从 The cat sat 开始，随后依次接上 on the mat .；代码则从 def square(x): 进入后续片段。这些都是固定续写，方便在重复实验时保持输入一致。

    先执行 Prefill，两层各自建立前缀的 K/V。随后让一个新 token 进入第一层：计算它自己的 Q/K/V，把新的 K/V 追加到这一层缓存，再让新 Query 读取这一层已有的历史 K/V，得到注意力输出，继续完成残差与逐位置变换。

    第一层完成以后，它的输出才进入第二层。同样的过程再发生一次，第二层也有自己的缓存。两层全部结束，界面才展示新位置的最终隐藏状态。

    我特意让缓存格按层、按阶段出现。因为如果一点击按钮，所有格子同时填满，很容易让人误以为整个模型共享一份缓存，或者新 token 的各层计算可以互相独立。逐层播放虽然慢了一点，但它把依赖顺序留下来了。

    这里还有一个经常被忽略的事实：新 Query 仍然需要读取越来越长的历史。KV Cache 省掉的是旧位置的重复计算，并没有消除新位置与历史之间的注意力计算。对这种标准密集注意力实现来说，解码一步的成本仍然会随上下文增长。

    用两条计算路径互相检查

    我希望页面不仅能把过程画出来，还能回答“这样复用到底对不对”。

    所以实验中有两条独立路径：一条在每次追加 token 后，把整个前缀完整重算；另一条保留旧缓存，只对新位置做增量计算。两条路径最终比较的是最后一个位置的隐藏状态。

    截图对应的步骤中，界面显示误差为零。这个数字的意义很具体：对于当前小网络、当前输入和当前步骤，缓存路径与完整重算得到了相同结果。它是一个可以复现的数值核对，并不是性能测试，更不是生产模型的精度报告。

    为了让这个核对可以读懂，演示网络只用了两层、四维表示和一个注意力头，包含确定性的表示、线性 Q/K/V 投影、因果 Attention、残差和逐位置非线性变换。它没有训练后的大模型权重，也没有 LayerNorm 和输出词表概率的 LM head。固定续写提供下一步输入，页面本身没有在采样生成句子。

    省下计算，也要付出存储

    缓存带来的另一个问题是显存。上下文越来越长，留下来的 K/V 也越来越多。

    The cost of remembering 面板把这笔账单独展开。需要计算的因素包括层数、KV heads、每个 head 的维度、token 数、batch size 和每个元素占用的字节数；Key 和 Value 各存一份，所以还要乘以二。

    保持其他条件不变，把上下文长度翻倍，这部分缓存就翻倍；把 batch 翻倍，同样如此。减少 KV heads 也会直接降低存储量，这能帮助理解 GQA、MQA 为什么会出现在推理优化的讨论里。

    这里用的是一个独立于两层演示网络的预算案例，估算范围只是 K/V 张量本身。模型权重、临时激活、内存分配、分页以及量化元数据都没有算进去。因此 512 MiB 不能被理解为运行整个模型只需要这么多显存，INT8 选项也只表示理想的张量字节数。

    三类模型，其实是三种信息路径

    看完缓存，再切换到 Model family atlas，几个熟悉的模型名称会变得更具体。

    Encoder-only 采用双向可见关系，一个位置可以读取输入中的其他位置。追加新的输入后，旧位置可能读到新内容，旧隐藏状态也就可能变化。因此不能直接照搬这里的因果前缀复用逻辑。

    Decoder-only 的目标位置只看自己和历史，正好对应前面逐步建立缓存的过程。Encoder–Decoder 则把两种路径放在一起：源端先形成表示，目标端做因果 self-attention，并通过 cross-attention 读取源端。

    当源端输入固定时，供 cross-attention 使用的源端 K/V 可以保持不变；目标端 self-attention 的 K/V 则随着生成持续增长。同样叫缓存，两者保存的对象和增长方式并不相同。把它们放进同一张信息流里，这个区别比单独背三类架构的定义更容易留下印象。

    我想让“推理优化”有一个可以追踪的起点

    LLM 推理还涉及批处理、调度、量化、算子和硬件，KV Cache 只是其中一部分。这个项目先把问题收在能够逐步算清楚的范围内：一个新 token 进来，哪些结果可以沿用，哪些必须新算，最后怎么验证。

    所有计算都在浏览器里完成，不需要 GPU 或外部推理服务。如果第一次体验，我建议先慢慢走完第一个新 token，再看数值误差，最后改变显存参数和模型家族。这样，“缓存”就不只是一个让模型变快的名词，而会对应一组具体的依赖、一份持续增长的存储，以及一个可以检查的结果。
